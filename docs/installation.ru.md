# Установка и обслуживание

[English](installation.en.md) · [Обзор проекта](../README.md)

Инструкция создаёт подключение для одного владельца на его собственных аккаунтах. Она не даёт помощнику разрешения входить в аккаунты, принимать новые условия, создавать ключи, выдавать доступ к почте или публиковать от вашего имени. Выполните эти шаги лично либо отдельно разрешите поддерживаемое действие. Пароли, OAuth-токены, Cloudflare credentials и приватные ключи нельзя вставлять в чат, исходники, issue или аргументы команд.

## 0. Проверьте доступность до создания ресурсов

1. Убедитесь, что вашему аккаунту доступен **приватный Site только для владельца, с D1 и provisioned MCP plugin**. Sites должен обеспечивать аутентифицированное размещение, plugin OAuth и доверенные заголовки `oai-authenticated-user-id` и `oai-authenticated-user-email`. Доступность может зависеть от аккаунта и workspace
2. Если это условие не подтверждено, остановитесь. Публиковать Site adapter как публичный raw Worker небезопасно даже с заданным email владельца. В этом релизе нет самостоятельного альтернативного сервера аутентификации
3. Подготовьте свой аккаунт Cloudflare с Workers/D1 и свой ящик Яндекса. Проверьте ограничения организации до включения IMAP и регистрации OAuth-приложения
4. Установите Node.js 24 LTS из официального источника. Минимум проекта: 22.15.0, включая `node:sqlite` для тестов. Для Windows нужен Windows 11. Wrangler официально поддерживает Windows 11, macOS 13.5+ и поддерживаемые Linux-дистрибутивы; Windows 10 не поддерживается. См. [требования Wrangler](https://developers.cloudflare.com/workers/wrangler/install-and-update/)
5. Проверьте квоты и расходы своих Cloudflare/Sites аккаунтов. Помощник установки не меняет тариф и не покупает дополнения, но обычные расходы действующего тарифа применяются. При неожиданном платном предложении или новых правах остановитесь

Контрольная точка: доступность приватного Sites и plugin подтверждена; `node --version` показывает подходящую версию. Доступ к почте ещё не выдан.

## 1. Выберите исходники или готовый release ZIP

Точный репозиторий: `chiginskiy/Yandex-mail-Dot-Connector`. Подготовленный release ZIP содержит `bridge/dist/bridge-wrapper.js`. Git checkout и автоматически создаваемый GitHub архив исходников требуют предварительной сборки:

```sh
git clone https://github.com/chiginskiy/Yandex-mail-Dot-Connector.git
cd Yandex-mail-Dot-Connector
npm ci --ignore-scripts --prefix bridge
npm ci --ignore-scripts --prefix site
npm run verify
```

Либо соберите только bridge:

```sh
cd bridge
npm ci --ignore-scripts
npm run build
```

`build` выполняется локально и ничего не публикует. Не заменяйте его командой `wrangler deploy` без `--dry-run`. Готовому ZIP всё ещё нужны Node и закреплённая версия Wrangler, но помощник может получить Wrangler через `npx` без установки всех зависимостей проекта.

На Windows сначала распакуйте архив в обычную папку пользователя. Не запускайте файлы внутри ZIP. Для проекта не нужны права администратора и изменение PowerShell ExecutionPolicy.

Контрольная точка: `bridge/dist/bridge-wrapper.js` существует; пакет не содержит состояние или настройки чужой установки.

## 2. Создайте закрытый bridge

Откройте терминал именно в **папке `bridge`**, где рядом находятся `windows`, `dist` и `package.json`.

Windows PowerShell:

```powershell
npx.cmd --yes --package=wrangler@4.145.0 node .\windows\setup.mjs check
npx.cmd --yes --package=wrangler@4.145.0 node .\windows\setup.mjs bootstrap
```

POSIX shell, тот же помощник:

```sh
npx --yes --package=wrangler@4.145.0 node ./windows/setup.mjs check
npx --yes --package=wrangler@4.145.0 node ./windows/setup.mjs bootstrap
```

Команда `check` проверяет CLI и локальную no-bundle сборку. `bootstrap` повторяет dry-run, затем:

1. Показывает временные права Cloudflare. Введите `LOGIN`, только если согласны; пройдите device-code вход на официальной странице Cloudflare
2. Показывает аккаунт, отдельное имя Worker и D1. Введите `CREATE`, чтобы создать именно эти ресурсы
3. Создаёт схему bridge и rate-limit bindings, публикует bridge с отключённой почтой
4. Просит точный публичный `https://…workers.dev` origin из результата deploy, без завершающего `/`; проверяет соответствие имени Worker и закрытый ответ
5. Печатает ваш точный callback Яндекса с окончанием `/oauth/callback`

При первом Worker Cloudflare может предложить регистрацию собственного поддомена `workers.dev`. Покупать домен не нужно. Namespace IDs лимитов выбираются случайно; при большом количестве существующих bindings проверьте отсутствие коллизий.

Состояние сохраняется в `bridge/.local/setup-state.json`. Не теряйте его. После частично успешного запуска не повторяйте bootstrap: помощник специально останавливается, чтобы не плодить ресурсы.

Контрольная точка: stage `bootstrap-complete`; Worker отвечает HTTP 503 с `connection_not_configured`; callback известен. На этом этапе 503 ожидаем. Токена Яндекса ещё нет.

### Права Cloudflare и очистка

Помощник запрашивает `account:read user:read workers_scripts:write d1:write`; Wrangler добавляет `offline_access`. Права действуют на аккаунт целиком, а не только на этот Worker. Временные credentials лежат в отдельной `bridge/.local/auth` в обычном формате Wrangler, без дополнительного шифрования приложением. Не открывайте и не пересылайте эту папку.

После входа помощник пытается выполнить logout и удаляет эту папку. После прерывания:

```powershell
npx.cmd --yes --package=wrangler@4.145.0 node .\windows\setup.mjs cleanup
```

Затем проверьте серверный отзыв в [Cloudflare Connected Applications](https://dash.cloudflare.com/profile/access-management/authorization), выбрав соответствующий grant Wrangler. Строка успешного logout не доказывает успешный серверный отзыв. Не удаляйте посторонние приложения и API tokens.

## 3. Зарегистрируйте своё приложение Яндекса

На [официальной странице Yandex OAuth](https://oauth.yandex.ru/) создайте собственное web-приложение:

- Redirect URI: точный callback из шага 2. `https://bridge.example.invalid/oauth/callback` здесь лишь нерабочий пример; в аккаунте нужен ваш реальный Worker origin
- Единственное право: **`mail:imap_ro`**, «Доступ на чтение писем в почтовом ящике». Не выбирайте `mail:imap_full`, SMTP и посторонние scopes
- Сохраните публичный Client ID. Здесь используется authorization code + S256 PKCE; копировать Client Secret или токен не требуется
- Проверьте доступ по IMAP и OAuth-токенам в настройках ящика; необходимые изменения подтвердите лично

Bridge запрашивает только `mail:imap_ro` и отклоняет другое право, если Яндекс вернул поле scope. Когда поле отсутствует, точные права зарегистрированного приложения и запроса остаются частью защиты. См. [OAuth Яндекс Почты](https://yandex.ru/support/yandex-360/business/mail/ru/web/security/oauth) и [PKCE](https://yandex.ru/dev/id/doc/ru/codes/code-url).

Контрольная точка: callback в приложении точно совпадает с bridge, почтовое право только на чтение. Регистрация приложения сама по себе не выдаёт доступ к ящику.

## 4. Создайте приватный Site

Используйте штатный процесс создания и публикации Sites, доступный вашему аккаунту. Импортируйте компонент **`site/`** в свой Site. Не копируйте идентичность чужого Site и не публикуйте adapter напрямую через Wrangler.

Регистрация, source/hosting metadata должны быть созданы для вашего проекта. Универсального project ID или готового `.openai/hosting.json` в пакете намеренно нет. Попросите помощника или интерфейс с доступом к Sites:

1. Создать server Site только для владельца, с MCP capability и штатным provisioned plugin OAuth
2. Использовать `site/src/site-worker.mjs` через собранный entry point `dist/server/index.js`
3. Подключить приватную Site D1 как `DB` и применить Drizzle migration из `site/db/schema.ts` и `site/drizzle/` штатным процессом миграций. Не создавать таблицы обработчиком HTTP-запроса
4. Задать `SITE_ORIGIN`: точный HTTPS origin Site; `BRIDGE_ORIGIN`: Worker origin из шага 2; `SITE_ID`: зарегистрированный ID Site; `OWNER_CHATGPT_EMAIL`: подтверждённый email вашего аккаунта
5. Оставить `OWNER_SITE_USER_ID` пустым только на начальном этапе с проверкой email; закрепить ID после шага 5
6. Проверить, что Site остаётся owner-only private и нет прямого публичного raw-worker обхода

Origin задаётся без пути, завершающего `/`, query и credentials. У Site и bridge **разные D1**. Site D1 хранит только ключи подписи; таблицы почтовых токенов bridge ей не нужны.

Контрольная точка: владелец открывает страницу настройки; анонимный и другой пользователь не могут вызывать почту и операции настройки. Ключ уже можно создать, но почта ещё не авторизована. Обнаружение tools само по себе не доказывает подключение почты.

## 5. Создайте ключ и настройте bridge

На приватном Site нажмите **Создать ключ связи**. Это создание постоянных credentials: приватного ключа Ed25519 в Site D1 и публичного JWK. Повторное нажатие показывает существующий ключ, а не заменяет его.

Скопируйте только публичные `SITE_ID`, `OWNER_SITE_USER_ID` и JWK. Добавьте этот точный `OWNER_SITE_USER_ID` в конфигурацию Site, сохранив проверку email, и обновите тот же приватный Site.

В `bridge` скопируйте `windows/connect.example.json` в `windows/connect.json`. Заполните шесть полей:

| Поле | Источник |
| --- | --- |
| `YANDEX_OWNER_EMAIL` | Ваш точный адрес ящика Яндекса |
| `YANDEX_CLIENT_ID` | Публичный Client ID вашего приложения |
| `SITE_ID` | ID вашего зарегистрированного Site |
| `OWNER_SITE_USER_ID` | Публичный ID владельца, возвращённый Site |
| `SITE_PUBLIC_KEY_JWK` | JSON-строка публичного Ed25519 JWK вашего Site |
| `SITE_ORIGIN` | Точный HTTPS origin вашего приватного Site |

`SITE_PUBLIC_KEY_JWK` должен быть JSON-**строкой**: внутренние кавычки в `connect.json` экранируются. Объект JWK со страницы нужно один раз сериализовать для этого поля. Обязательны `kty: "OKP"`, `crv: "Ed25519"` и публичный `x`; приватное поле `d` запрещено. Не подставляйте придуманные ключи из примеров.

Если существует `bridge/.local/connect.json`, помощник предпочитает его, иначе читает `bridge/windows/connect.json`. Проверьте, какой файл редактируете. Оба относятся к локальным данным установки и исключаются из релиза.

```powershell
npx.cmd --yes --package=wrangler@4.145.0 node .\windows\setup.mjs configure
```

Для POSIX замените `npx.cmd` на `npx` и путь на `./windows/setup.mjs`. Помощник проверяет настройки до входа, показывает прежний Worker и список папок, просит `CONFIGURE`, затем `LOGIN`. Он обновляет исходный Worker, сохраняя D1. Разрешение Яндекса не выдаётся этой командой.

Контрольная точка: stage `configured`; прежние Worker/D1 и Site сохранены; Site и bridge закрепляют одного владельца и согласованную пару ключей. Ещё раз проверьте отзыв временного Wrangler grant.

## 6. Разрешите почту и подключите plugin

1. На приватном Site нажмите **Подключить Яндекс Почту**
2. Убедитесь, что открыта официальная OAuth-страница Яндекса и запрошено только чтение; войдите как владелец указанного ящика и подтвердите
3. Callback одноразово погашает state, обменивает code на сервере, проверяет XOAUTH2 для закреплённого ящика и сохраняет access token в bridge D1. Приватный токен не показывается Site или MCP-клиенту
4. Браузер возвращается на фиксированный origin вашего Site с подтверждением авторизации
5. Подключите provisioned plugin этого Site через штатный процесс платформы. Не создавайте второй MCP OAuth-сервер и локальное подключение для обхода защиты

Автоматического refresh нет: bridge намеренно не сохраняет refresh token. По истечении срока или после отзыва владелец подключается заново.

Контрольная точка: владелец видит пять tools и получает успешный ответ малого `yandex_mail_list`. До практического использования выполните smoke-проверку.

## 7. Начальная smoke-проверка

Используйте небольшое известное тестовое письмо в своём ящике. Инструкция не отправляет его за вас.

- [ ] Анонимный и другой пользователь не могут читать почту и создавать ключ
- [ ] `yandex_mail_folders({})` возвращает ограниченные метаданные; список папок не расширяет права
- [ ] `yandex_mail_list({"mailbox":"INBOX","limit":1})` возвращает малую страницу
- [ ] `yandex_mail_search({"mailbox":"INBOX","subject":"Connector test","limit":1})` возвращает тестовое письмо либо cursor для продолжения
- [ ] `yandex_mail_read` с возвращёнными UID и UIDVALIDITY читает текст; сравнение флагов до/после подтверждает отсутствие изменений
- [ ] Малое выбранное тестовое вложение проходит проверки частей/метаданных/хэшей и совпадает с известным локальным оригиналом
- [ ] Запрещённая папка отклоняется; HTML не загружает внешние изображения; почта и токены не появляются в логах приложения

Это проверки конкретного развёртывания, которые выполняет установщик. При подготовке релиза новая live-установка таким образом не проверялась. Примеры: [API](api.md).

## Необязательный доступ к отправленным

Вызовите `yandex_mail_folders`. Используйте только точный возвращённый `path`. Предпочтителен `sentStatus: "server_identified"` с одним подтверждённым сервером кандидатом. При неоднозначности, усечении discovery или определении только по имени выберите папку явно; не угадывайте перевод названия.

Добавьте `SENT_MAILBOX` в существующий файл подключения и снова запустите `configure`. Значение должно отличаться от `INBOX`. Помощник разрешит `INBOX` плюс этот точный путь. Discovery сам прав не выдаёт. Чтобы убрать отправленные, удалите только `SENT_MAILBOX` и повторите `configure`.

## Обновление

1. Запишите текущие версии компонентов. Сохраните приватную резервную копию настроек и `bridge/.local/setup-state.json`. Бэкапы баз и сведения для rollback храните приватно: они могут раскрывать credentials
2. Прочитайте [CHANGELOG](../CHANGELOG.md), схемы и [verification](verification.md). Не считайте будущую миграцию БД автоматически обратимой
3. Распакуйте новый релиз отдельно, сравните файлы программы и обновите действующую установку, сохранив `.local`, свой connect-файл, Worker/D1, Site, ключи и Yandex app
4. При обновлении исходников повторите `npm ci` и `build`. Из существующего `bridge` запускайте `configure`, не `bootstrap`
5. Обновите соответствующий Site adapter штатным приватным процессом того же Site. Сохраните project ID, D1, owner configuration и provisioned plugin
6. Проверьте установленную схему tools и повторите небольшую smoke-проверку. Действующий mail grant обычно сохраняется при обновлении только кода; без причины не меняйте ключ и не выдавайте разрешение заново

Если раньше bridge находился в плоской папке, используйте эту папку как прежний корень bridge либо осознанно перенесите её local state и connect-файл в новую `bridge/`. Не создавайте второй bridge случайным bootstrap из новой структуры.

## Откат

Остановите новые вызовы почты и определите ранее работавшую **совместимую пару bridge/Site**. Восстановите её проверенный код/сборку либо выполните rollback версий развёртывания через соответствующие сервисы. Сохраните ресурсы и публичные настройки. Не восстанавливайте старый D1 backup только ради отката кода: он может вернуть отозванный токен или нарушить соответствие ключей/state.

У первого публичного релиза нет предыдущего публичного релиза, который можно рекомендовать для отката. Если независимо проверенной совместимой версии нет, отключите подключение и выясните причину. Не откатывайтесь на заведомо уязвимый код. После восстановления повторите проверку изоляции владельца и read-only smoke.

## Отзыв доступа и удаление

- **Остановить почтовый доступ:** отзовите это приложение в разрешениях подключённых приложений Яндекс ID. Удаление plugin из dot само по себе не отзывает токен Яндекса
- **Остановить Site-to-bridge:** отключите подключение или уберите/замените закреплённый публичный ключ в управляемом вами deploy bridge. Ротация требует согласованных действий в обоих компонентах; в простой UI нет кнопки ротации
- **Убрать Cloudflare grant:** выполните cleanup и проверьте отзыв Wrangler в Cloudflare Connected Applications
- **Удалить инфраструктуру:** точно определите ресурсы этой установки, решите вопрос приватных бэкапов, затем удалите её Site, Worker и отдельные D1 через соответствующие сервисы. Удаление баз необратимо и никогда не выполняется помощником автоматически
- Удаляйте локальные вложения и checkpoints, когда они больше не нужны. Не отправляйте `.local/auth`, D1 exports или письма для диагностики

Отзыв у провайдера и удаление локального файла являются разными действиями. См. [безопасность](security.md) и [диагностику](troubleshooting.md).
